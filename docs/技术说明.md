# DeepEggy 技术说明

> 项目：DeepEggy · 配料表翻译官（拍照/扫码 → 逐项释义 → 量化折算 → 个性化提醒 → 分享卡片）
> 说明对象：评委、队友、后续接手的人
> 版本：2026-11-22 17:00（代码提交 `a24d7ba`）
> 在线 Demo：https://182-92-231-87.sslip.io/

---

## 一、解决什么问题

超市货架前的三个具体困难：

1. **看不懂**：配料表里「结晶果糖」「卡拉胶」「TBHQ」这些词，消费者不知道是什么、为什么要加。
2. **算不清**：「0 蔗糖」「无添加糖」这类话术，与实际含糖量对不上；营养成分表上的克数没有直观参照。
3. **不敢买**：过敏体质、控糖控盐人群，需要一个明确的「我能不能吃」的判断。

产品做法：拍一下包装（或扫条码）→ OCR 识别 → 逐项释义 → 换算成方糖/盐勺 → 拆穿话术 → 按个人健康标签单独提醒 → 生成一张可分享的卡片。

## 二、系统架构

```
┌─────────────────────────── 手机 / 桌面浏览器 ───────────────────────────┐
│  纯静态 SPA（无构建步骤）                                                │
│  index.html + app.js + ingredient-tree.js + mock.js                     │
│  zxing-wasm/JS 条码解码 ｜ getUserMedia 相机 ｜ Canvas 分享卡片           │
└───────────────────────────────┬─────────────────────────────────────────┘
                                │ HTTPS / JSON
┌───────────────────────────────▼─────────────────────────────────────────┐
│  后端：Python 标准库 http.server（零第三方依赖，ThreadingHTTPServer）      │
│  main.py 路由 + 静态托管                                                 │
│   ├─ analyze.py      配料解读编排（LLM + 知识库 + 词条 + 过敏原）          │
│   ├─ label_name.py   包装文本 → 商品名/品牌抽取（规则 + 词典）             │
│   ├─ label_ner.py    BIO + 平均感知机字段抽取（生产商/地址/标准号/SC）      │
│   ├─ barcode_lookup.py 条码三级查询 + 联网搜配料表                        │
│   ├─ reviews.py      口碑抓取（5 个搜索源）+ AI 归纳                      │
│   ├─ trace.py        六阶段溯源证据链（不编造，缺口写 gaps）               │
│   ├─ trace_search.py 溯源检索 + SQLite 缓存                              │
│   ├─ kb.py           GB 2760 知识库只读层                                │
│   ├─ product_names.py 商品名规范化/品牌展示                               │
│   └─ ocr_cloud.py    百度智能云 OCR 适配（可选 ocr.py = PaddleOCR-VL）    │
└───────────────────────────────┬─────────────────────────────────────────┘
                                │
        ┌───────────────────────┼──────────────────────────┐
        ▼                       ▼                          ▼
   DeepSeek API            百度 OCR / PaddleOCR       搜索与数据源
   (deepseek-chat)         (图片转文字)               Tavily / 头条 / 神马 / 夸克
                                                      OpenFoodFacts / GB 2760 本地库
```

设计取舍：

- **后端零依赖**：只用 `http.server` + `sqlite3` + `urllib`，任何装了 Python 3.10+ 的机器都能直接跑起来，不依赖 pip 安装和 C 扩展。
- **前端零构建**：没有 npm / webpack，改完刷新即可，方便赛期内快速迭代和多端验证。
- **LLM 只做「解释与归纳」**：所有数字、来源、评价必须有出处或明确标注为推断。

## 四、四条核心链路

### 4.1 扫条码 → 商品身份 → 配料表

```
相机取景（zxing 解码）
  └─ GET /api/scan-barcode?code=xxx
       ├─ ① 内置示例库（4 款）
       ├─ ② 本地商品索引（543 款，OpenFoodFacts 中文化 + 补充抓取）
       ├─ ③ GTIN 等价码匹配（EAN-13 / UPC-A / GTIN-14 / 校验位变体）
       └─ ④ 联网兜底：OpenFoodFacts 在线 → 编码中心备案数据
  └─ 命中商品身份 → POST /api/analyze-barcode
       ├─ 联网搜配料表（Tavily / 免费搜索）
       ├─ LLM 严格提取（品牌/品类/口味词必须一致，否则 found=false）
       └─ 提取失败 → AI 按品牌品类推断，结果明确标注「推断」
  └─ 返回结构化 product → 结果页
```

关键设计：**宁可不给，也不张冠李戴**。同品牌不同口味算不匹配；没搜到就标注「按同类配方推断」，绝不冒充真实配料表。

### 4.2 拍配料表

```
拍照 → Canvas 压缩（长边 ≤1600, JPEG）
  └─ POST /api/ocr  →  百度智能云 OCR / 本地 PaddleOCR-VL
  └─ 核对页：低置信词高亮，用户可手改
  └─ POST /api/analyze（文本）
       ├─ 配料切分（顿号/逗号/括号感知）
       ├─ GB 2760 知识库注入（CNS 号、功能类别、使用范围）
       ├─ 208 条人工词条注入（优先采用团队释义）
       ├─ 过敏原检测（35 类，含别名与交叉反应）
       └─ LLM 输出结构化 JSON（配料/营养/话术/搭配/健康/溯源）
```

### 4.3 微信扫了码（截图输入）

微信扫码无法被网页调用，因此提供「截图给我看」：截图 → OCR → `label_name.py` 抽出商品名/品牌 → 走 4.1 的联网解读。

### 4.4 商品索引

首页展示 543 款可查商品，按 11 个品类标签筛选；点击等同扫码命中，直接走解读链路。

## 六、AI 编排与「不编造」机制

| 环节 | 做法 | 防编造手段 |
|---|---|---|
| 配料释义 | LLM 逐项解释，注入 GB 2760 与团队词条 | 提示词写死「数字以文本为准、读不到写未标注」；配料名以本地切分结果为准，模型只能解释不能替换 |
| 营养折算 | 按国标 NRV 折算方糖/米饭/盐勺 | 没有营养数据就整块留空，让模型留空数组 |
| 话术拆穿 | 识别「0 蔗糖」「无添加」等表述 | 只对文本中存在的表述做判断 |
| 口碑归纳 | 5 个搜索源抓原文 → LLM 归纳 | 每条评价带来源域名；0 条时 `taste` 全 0 并标注「未做口味评分」 |
| 溯源 | 六阶段证据链 | 查不到的写进 `gaps`，不补全、不猜测 |
| 联网配料表 | LLM 从网页正文提取 | 品牌/品类/口味三重一致性校验；提取不到就走「推断模式」并标注 |

**模型**：DeepSeek `deepseek-chat`（OpenAI 兼容协议，可换 `DEEPSEEK_MODEL`）。
**成本控制**：解读结果按「配料文本 + 过敏原 + 商品身份 + 模式」做进程内缓存（1 小时 TTL / 上限 50 条），口碑缓存 30 条。

## 八、算法细节

### 8.1 配料切分

按顿号/逗号/分号切分，但**括号内不切**（复合配料），并对「水」这类单字合法配料单独保留；OCR 粘连时用关键词边界截断（保质期/净含量/许可证等）。

### 8.2 字段抽取（`label_ner.py`）

- 自写 BIO 标注 + 平均感知机（Averaged Perceptron），离线可推理；
- 抽 4 个字段：生产商、地址、标准号、SC 证号；
- 训练数据是**模板生成的合成银标**，指标与局限如实记录在 `data/training/dataset_info.json` 与开发日志；**从未用它作为溯源结论的依据**（`used_for_trace_evidence: false`）。

### 8.3 条码与 GTIN 等价

`_equivalent_gtins()` 生成同一商品的不同书写形式（EAN-13 / UPC-A 前导 0 / GTIN-14 / 校验位变体），避免「同一个商品不同码」查不到。

### 8.4 口碑相关性闸门

原实现要求完整商品名连续出现，中文商品名会被大量误杀。现改为三条任一命中：

1. 完整商品名（去空格）出现；
2. 品牌出现 + 商品名任意 2 字片段出现；
3. 商品名任意连续 3 字出现（挡住「经典原味薯片 → 经典」这类字典解释）。

### 8.5 溯源字段边界

OCR 常丢换行，字段会串行。用 `FIELD_CUT` 正则在下个关键词处截断，边界词包含：厂址/地址/产地/电话/配料/保质期/委托方/**受托方**/受委托方/监制方/生产商/生产企业/标准号/许可证/净含量/储存条件/营养成分。

## 十二、已知限制（不回避）

1. **OCR 依赖外部服务**：没有百度 Key 时 `/api/ocr` 返回 501，前端降级为手动输入；本地 PaddleOCR-VL 需要 NVIDIA GPU。
2. **扫码覆盖率有限**：本地 543 款 + OpenFoodFacts 在线，冷门商品会提示「改走拍配料表」。这是数据覆盖问题，不是识别失败。
3. **联网搜配料表成功率约 50–60%**：配料表常以图片形式存在于商品页，文本检索拿不到；失败时明确标注为 AI 推断。
4. **字段抽取模型训练于合成数据**：不含真实包装照片，指标不代表真实场景准确率，也未用于溯源结论。
5. **单次 AI 解读 6–30 秒**：受外部 API 与检索影响。
6. **搜索源受反爬影响**：百度 PC 版基本拿不到结果，已改用移动版/搜狗/360 兜底。
7. **未接微信扫码**：微信扫一扫无法被网页调用（需公众号 JS-SDK 与备案），改为「截图给我看」。
