## 一、一句话定位

DeepEggy 是一个**配料表解读网页应用**：拍包装或扫条码 → 拿到真实配料表 → 把每一味配料翻成大白话、按国标折算糖盐油、按用户健康状况与过敏原点名提醒 → 生成可分享的卡片。

## 二、系统架构

```
浏览器（零构建静态 SPA）
   │  fetch JSON
   ▼
Python 标准库 http.server（零第三方依赖，13 个 API）
   ├── 条码三级查询：本地库 → OpenFoodFacts 在线 → 编码中心备案
   ├── 联网检索：Tavily / 自建免费搜索（头条、神马、夸克）
   ├── LLM 解读：DeepSeek（结构化 JSON 约束）
   ├── OCR：百度智能云（本地可选 PaddleOCR-VL）
   └── 本地知识库：GB 2760 添加剂、食品分类、配料通俗词条、过敏原
```

- **前端**：`app/frontend/` 纯静态（HTML/CSS/原生 JS），无打包、无框架；相机取景与条码识别、OCR 核对页、7 个结果 Tab、Canvas 分享卡片。
- **后端**：`app/backend/` 单文件 `http.server`，仅用标准库；对话式 API 全部返回 JSON。
- **部署**：阿里云轻量 2C2G，`systemd` 双服务（80 HTTP / 443 HTTPS），代码在 `/root/deepeggy`。

## 三、关键链路

1. **识别**：扫码（BarcodeDetector / 手动输入）或拍照 OCR，识别结果先进「核对页」让用户确认，低置信词高亮。
2. **取配料表**：条码命中本地库直接读；未命中走 OpenFoodFacts 在线，再走编码中心备案拿商品身份（名称/品牌/规格），最后联网搜配料表。
3. **防张冠李戴**：LLM 提取时校验品牌、品类、口味词与商品身份一致；提取不到就明确标注「按同类配方推断」，不冒充真实配料表。
4. **解读**：逐项释义（是什么/为什么加/要注意什么）→ 量化折算（按国标给出每份糖盐油对应的方糖与盐勺）→ 话术拆穿（如「0 蔗糖 ≠ 无糖」）→ 个性化提醒（过敏原、健康状况）→ 溯源（标准号、生产商、产地）→ 口碑（联网抓取并标注来源）。
5. **商品索引**：`/api/products` 提供清洗过的商品库（当前 543 款），带品类标签与热度信号，点一条即走同一条解读链路。

## 四、数据与知识库

| 数据 | 规模 | 来源 / 许可 |
|---|---|---|
| 商品库（清洗后进首页） | 543 款 | OpenFoodFacts（ODbL）+ 联网补抓 |
| 商品库（原始存档） | 837 条 | OpenFoodFacts（ODbL） |
| 食品添加剂 | 642 条 + 使用范围 30,429 条 | GB 2760-2024（公开国标） |
| 食品分类 | 388 类 | GB 2760-2024 配套分类 |
| 配料通俗词条 | 208 条（含 49 别名） | 团队人工整理 + 复核 |
| 过敏原 | 35 类（14 类核心 + 21 类扩展） | GB 7718-2025 + 花粉-食物交叉反应 |
| 标签字段抽取模型 | 自研 BIO + 平均感知机 | 合成银标训练（非真实照片），指标与局限在开发日志中如实记录 |

**数据清洗是这轮的重点工作之一**：众包库里混着非食品（镜头湿巾、酒精、香烟）、纯外文名、只有品牌名的条目。我们加了品名规范化层（品牌/系列 + 具体品名 + 商品名词库），把 852 条原始索引清洗到 543 款能对上货架的商品；条码查询不受影响。

## 五、AI 使用与人工把关

| 环节 | 用了什么 | 把关方式 |
|---|---|---|
| 配料解读 | DeepSeek API | 提示词写死「数字以文本为准、读不到写未标注、不编造」；结果标注「AI 生成」 |
| 联网搜配料表 | Tavily + 免费搜索 → LLM 严格提取 | 品牌/品类/口味一致性校验；搜不到标注「按同类配方推断」 |
| OCR | 百度智能云 / PaddleOCR-VL | 用户核对页确认后才进入解读 |
| 口碑归纳 | 联网抓公开结果 → LLM 归纳 | 每条标注来源，抓不到就写「网上评价较少」 |
| 开发过程 | AI 编程助手 | 产品方向与取舍由团队决定，决策与实测按小时记在开发日志 |

## 六、工程质量与验证

- **自动化测试**：`pytest app/tests` 70 项（含商品名清洗、配料抽取、溯源字段、NER 等回归用例）。
- **可追溯**：`docs/开发日志.md` 按小时记录改动、原因、验证方式与失败尝试（含这次商品索引清洗的完整来龙去脉）。
- **可复现**：仓库含数据构建脚本（`scripts/`），知识库文件由脚本重跑产出。
- **接口文档**：`docs/后端接口说明.md` 列全部 13 个接口的入参、出参与错误约定。

## 七、已知局限

1. 众包商品数据质量参差，清洗规则只能覆盖常见情况，长尾仍可能有个别错配（已在索引层做兜底过滤）。
2. 联网检索依赖第三方搜索与网页质量，极端情况下只能给出「按同类配方推断」。
3. OCR 受拍摄角度与反光影响，故设计成「识别 → 用户核对 → 解读」。
4. 自研字段抽取模型使用合成数据训练，真实照片上的泛化有限，定位为辅助而非主链路。
5. AI 解读为通俗化解释，不构成营养或医疗建议；页面已做声明。
